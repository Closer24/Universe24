# Contributing

Contributions are welcome: a bug found in the implementation, a derivation checked, a world built by the paper's method, a formula tested against a measurement. The way in is a fork, a branch and a pull request, read against the law and the architecture like any change; the project's own changes go in by the road of [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), section 4, and `main` moves only by the Boss's fast-forward of a candidate the writer has approved (the roles: How we work, in the same document). The papers' text in `papers/` (the first paper in `papers/one_rule/`, the time paper in `papers/spacetime_events/`) is the version of record, and changes to it are the author's.

Universe24 is the implementation of the law in [docs/ALGEBRA.md](docs/ALGEBRA.md), told part by part in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). The engine is Tensor24 (`src/tensor24/`); the engine the paper reports is the tag v1.1.0, run from the tag, and main carries version 4.0.0 until Tensor24 is released (what changed in [CHANGELOG.md](CHANGELOG.md)). A change of the engine enters only as the implementation of a law line of [docs/ALGEBRA.md](docs/ALGEBRA.md), and only when its derivation stands as DERIVED and READY in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), by pull request. A contribution is read against the law.

## The ground rules

- A physics change starts from the law's line in `docs/ALGEBRA.md`, the open things listed by name in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), and passes the property tests of `tests/frame.py` (locality, purity, rename, the 24's images, the run back) before it enters; a hypothesis that needs more is stated under its own name.
- The engine matches the law in its implementation, not only in its results: the step is one act at every Node-clock (`src/tensor24/engine/`), every division Rule3's carry, written once in `src/tensor24/algebra/carry.py`; each folder imports only what the architect's table allows ([docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)), and the gate refuses a push that breaks it.
- Physical calculations use whole numbers of any size, the Node-clock's own gears and its six Meshes' gears; nothing is kept at a Node-clock beyond the law's own numbers, and the engine holds no number of physics: every value comes from the three files.
- A click is the one measurement; a reading of the board's numbers is a diagnostic and is labelled so. Runs and tests are headless: inspect a run's record and its ledger, never a frame.
- Each generic part has one small test of its contract, then the whole runs once on the example (docs/ALGEBRA.md, line 106); no test pins the numbers of an example world.
- A change to a document replaces what it touches and deletes what no longer holds, in the same pull request; a document cites a path in backticks only where the tree holds it.
- Everything in the repository is in English and ASCII, comments, docstrings, documents, test descriptions and identifiers alike; `tools/documents_gates.py` checks the text files.

The gates are the rule for the engine: whole numbers only; no float, no root, no circular function that makes a phenomenon happen, no table, no loop that makes a formula, no number beyond 0 and 1 in the code, and no division that is not Rule3's (`tools/derivations/open_items/scribe_scan.py`, [SCRIBE-GATE-1.md](tools/derivations/open_items/SCRIBE-GATE-1.md)); a push that raises a count of one of these is refused. A change that needs any of these is not an engine change; it is a line of the law first.

## The checks

With Python 3.14 or later, which `pyproject.toml` requires, format and check the changed Python files with `python -m ruff format` and `python -m ruff check`, then run `python tools/check.py`: it selects the changed files and their consumers and runs Ruff, strict mypy, the gates and the tests they need (`--dry-run` prints the selection, `--tests` adds a dependency the selector cannot see, `--full` is the explicit complete audit). Never drop a related failing test or disable a gate.

## Pull requests

Keep a pull request small and focused, one task, with its code, its tests and its documents together; state the problem, the change, the validation and which tests were not run. Never commit secrets, installed environments, caches or run outputs (`runs/`, `artifacts/`). A model hypothesis is reported as a hypothesis, never as proof of real-world physics. A release is a tag on `main` with a GitHub release; the GitHub-Zenodo integration archives it on Zenodo with the metadata of `.zenodo.json`, and the housekeeping after it names the version DOI in `CITATION.cff`, [CHANGELOG.md](CHANGELOG.md), [README.md](README.md) and `llms.txt`.

## Reporting an error, a mismatch or a failed reproduction

A report is a contribution. Open an issue with the template `.github/ISSUE_TEMPLATE/report.md`; it asks for what an answer needs: the version read (the tag, the Zenodo DOI or the commit), the claim by its name (a bold line of [docs/ALGEBRA.md](docs/ALGEBRA.md), a section or an equation of a paper), the command run with its environment, what was expected and what came out, and the source compared against (a measurement with its reference, a derivation, a run). Four kinds of report are answered: a mathematical error in a derivation, a disagreement with a measurement, a reproduction that fails, and a criticism of the model's assumptions; the first three by a check (under `tools/derivations/` for a derivation or a measurement, the engine's tests for a run) and, where the check confirms the report, a corrected line of the law, holding its new wording alone; the fourth by a line of section 6, what is open, of [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) or an answer in the issue. A finding against the version of record of a paper is answered in the issue, the published file unchanged.
