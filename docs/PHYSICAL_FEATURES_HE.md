# איך מוסיפים פיצ׳ר פיזיקלי

מטרת הנוהל: חוק שאפשר להבין, לבדוק ולהחליף בנפרד מהעולם שמשתמש בו.
העקרונות המחייבים הם ב־[הגדרות הסימולטור](../SIMULATOR_DEFINITIONS.md)
וב־[ארכיטקטורה](ARCHITECTURE.md). הנוהל אינו משנה אותם.

## 1. כותבים חוזה לפני קוד

בתיאור השינוי ממלאים את הטבלה. אין צורך במערכת תצורה חדשה לכל פיצ׳ר.

| חלק | מה מגדירים |
| --- | --- |
| החוק | הפעולה המתמטית המקומית וההנחות שלה; מה משתנה לעומת המודל הקיים |
| קלטים | שמות, משמעות, יחידות, טווחי שלמים ומאיזה מידע מקומי כל ערך הגיע |
| מצב מתפתח | אילו ערכים נשמרים בין עדכונים, מי מחזיק אותם ומה גודלם הקבוע |
| פרמטרים | קבועים למשך הרצה, משמעותם, מקורם, תחומם והייצוג הרציונלי שלהם |
| ערכים נגזרים | מה מחושב מהקלט במקום להישמר שוב כמקור אמת נוסף |
| פלט | רשומה קבועה של תוצאה או הצעת שינוי, כולל שאריות וחילופי תנע כנדרש |
| חוזי עקביות | קשרים בין ערכים, סדר קריאה וכתיבה, גבולות וסוגי שגיאה |
| בדיקות | קלט מספרי, תוצאה צפויה שנקבעה באופן עצמאי ומקרי גבול |

״קלט מפורש״ אינו בהכרח משתנה בלתי־תלוי בפיזיקה. למשל, ערך ושארית כפופים
למכנה; מהירות המחושבת מתנע אינה פרמטר חופשי נוסף. מתעדים את הקשרים
ומאמתים אותם, במקום להחזיק שתי גרסאות סותרות של אותו גודל.

## 2. מפרידים אחריות

- `fields/` או `dynamics/`: החישוב המשותף, פונקציה או רכיב עם פרמטרים
  בלתי־משתנים. הקלט והפלט מפורשים; אין גישה לעולם, ל־Config הכולל,
  לזהות התרחיש או למשתנים גלובליים משתנים. מצב מתפתח, כולל שאריות,
  מתקבל בקלט ומוחזר בפלט; הוא אינו מוסתר בתוך אובייקט החוק.
- `core/`: חוזי מצב קבועים, כתובות, תזמון, אימות והחלת הצעות. הרחבת מצב
  מחייבת החלטה מפורשת; אין להוסיף מפות הולכות וגדלות לכל מקור או תא.
- `models/`: בחירת חוק ומדיניות, חילוץ ערכים מהרשומות והעברתם לרכיב.
  כאן לא מחשבים שוב את הנוסחה, גם במודל חדש או בתיקיית משנה.
- תצורה ו־API: ערכי הפרמטרים והרכבת הרכיבים. משתמשים בתצורה הקיימת
  כשהיא מתאימה; רכיב גנרי מקבל רק את הפרמטרים הדרושים לו, או רשומת
  פרמטרים קטנה וגנרית. שינוי בזמן ריצה הוא מצב או קלט, לא ״קבוע״ חבוי.
- `scenarios/runner`: תנאי התחלה והרצה. `diagnostics/`: מדידות ותצוגה
  בלבד; תוצאות המדידה אינן מוזנות בחזרה לחוק לתיקון העולם.

הפרדת רכיבים אינה מחייבת להעביר כל סקלר בפונקציה אחרת. שומרים יחד
פעולות שחייבות לקיים חוזה משותף, כמו דחף החלקיק והדחף הנגדי של השדה.

## 3. דוגמה קיימת: מתיחת קשר

`fields/geometry.py:MeanStretch` מחזיק פרמטרים קבועים: בסיס, מונה ומכנה.
בקריאה הוא מקבל שני ערכי שדה: מקומי וערך שהגיע מהשכן. הוא מחזיר אורך
שלם מוצע; אינו מאתר שכנים, אינו משנה קשר ואינו מתזמן הודעה.

המודל בוחר את הפרמטרים; רכיבי הקשרים אחראים להעברה ולהחלה בזמן הנכון.
אפשר לבדוק את החוק בלי להריץ עולם:

| פרמטרים: בסיס, מונה, מכנה | קלט מקומי, קלט שהתקבל | אורך צפוי |
| --- | --- | --- |
| 100, 1, 1 | 0, 0 | 100 |
| 100, 1, 1 | 10, 10 | 110 |
| 100, 1, 2 | 10, 10 | 105 |

זו דוגמת מבנה מתוך המודל הניסיוני, לא טענה שהנוסחה היא חוק טבע מוכח.

## 4. מוכיחים את ההפרדה בבדיקות

1. בדיקת החוק הגנרי: דוגמאות מספריות, שאריות, אפס, סימטריות שהובטחו,
   קלט פסול וחריגה מהטווח. בודקים גם שינוי פרמטר כשהקלט נשאר קבוע.
2. בדיקת המודל המסוים: הוא בוחר את הרכיבים והפרמטרים שהוגדרו ומפיק
   את התוצאה המצופה. אין להסתפק בכך שהפלט שווה לקריאה חוזרת לאותה נוסחה.
3. בדיקת שילוב: החלפת חוק דרך הממשק, בלי לשכתב מנוע או להעתיק נוסחה;
   אימות תזמון, מקומיות וחילופי תנע בהתאם לחוזה.
4. רגרסיה: מודל הבסיס נשמר. חוק חדש בעל התנהגות אחרת מקבל זהות מפורשת
   ותוצאות נפרדות; אין לשנות את הגרסה הקפואה כדי להעביר בדיקה.

מריצים את שערי האיכות לפי AGENTS.md. בדיקת הטיפוסים מכוונת לגרסת Python
של ההרצה; מטריצת CI בודקת בנפרד את 3.11 ואת 3.12. כל הרצת עולם מצורפת כ־HTML דרך
מסלול התצוגה הקיים; בדיקה של פונקציה מקומית בלבד אינה דורשת הרצת עולם.
מוסיפים ציפיות ל־[מפת הבדיקות](TEST_EXPECTATIONS_HE.md).

## 5. בודקים את גבול ההרחבה

לפני הוספת שדה וקטורי, מספר שדות או שכבת קוונטים, בודקים אם חוזי המצב
והתזמון תומכים בהם. היכולת להחליף חוק סקלרי אינה תמיכה אוטומטית בכל מצב
חדש. שינוי פוסטולט או סכמת מצב מתועד ונבדק במפורש, בהתאם להרשאת המשתמש.
בדיקות סטטיות אוכפות חלק מהגבולות; ביקורת קוד בודקת גם תלות מוסתרת
ומצב חיצוני שאין להן יכולת להוכיח או לשלול באופן מלא.
